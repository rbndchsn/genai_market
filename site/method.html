How it was built

This site was made by one person directing one AI coding agent over about two days. This page explains how, so that you can do the same, whether you are writing your first script or running an engineering team.

The setup

Tools. Visual Studio Code as the editor, with Claude Code running in its terminal. Claude Code is Anthropic's command-line agent: it reads and writes files in the project folder, runs commands, opens a headless browser, and reports back. The model behind it was Claude Fable 5.1 for almost every session. Python 3.11 for the extraction and check scripts, plain HTML, CSS and JavaScript for the site, Git and GitHub Pages for publishing.

Division of labour. The agent did the research reading, the synthesis, the code, the debugging and the visual review. The human set the goal, chose the sources, downloaded the reports that sit behind a sign-in, made the judgement calls, looked at the live site, and said yes or no before each commit. Neither could have produced this alone in the time. The agent has no memory between sessions and no taste of its own. The human does not have two days to read twelve reports end to end.

Scale. The numbers below are read from the site's own data files at the moment you load this page.

Start with a plan, not a prompt

The single most important decision was made before any code: the project would be run from a plan file, and the agent would read it first in every session. Two Markdown files did all the coordination.

The instructions file

A short file that every session of the agent reads automatically. It says, in order: read the plan in full before doing anything; find the first unfinished step; work only on that step; when it is done, tick it in the plan with a date and a note; record decisions and open questions in the plan, never only in chat; update the status block before finishing. It also carries the non-negotiable content rules and the project's few technical facts, such as which Python to use and where the sources live.

The plan file

A living document with a fixed shape: a status block at the top (last updated, current phase, next step, blockers), the project overview and goals, the source inventory, the architecture, the implementation steps grouped into phases with a checkbox each, a decisions log, a list of open questions, and a change history. Steps are never deleted or rewritten. A finished step keeps its note about what was done, what was verified and what was fixed, so a later session can see the reasoning without re-deriving it.

Why this works

An AI agent starts every session with an empty memory. Without a plan, each session begins by guessing what the last one did, and the guesses drift. With a plan, the session reads a status block and continues from the exact step, in the same style, under the same rules. The plan also turned out to be the best place to think. Writing a step down before doing it exposed vague steps, and the decisions log kept the same question from being reopened three times.

The plan was also where scope was defended. When the agent noticed something that should be done later, the rule was to add it to the plan as a new step, not to do it now. That one rule prevented most of the sprawl that makes agent projects hard to review.

If you are starting out

Make two files before your first prompt: one that tells the agent how to work, one that lists the steps. Ask for one step at a time. Look at the result before asking for the next.

If you run teams

Treat the plan as the state machine and the agent as a stateless worker. Everything a human reviewer needs, including the reason for each decision, has to be in the file, because the chat is gone tomorrow.

The steps

Eight phases, in the order they ran. Each phase was a group of numbered steps in the plan, and each step was done, reviewed and ticked before the next began.

  1. Scaffolding. Write the instructions file and the plan skeleton. Nothing else. This took minutes and paid for itself the same day.
  2. Scope. A short conversation to settle the goal, the audience, the stack and the feature list. The answers went into the plan's overview and goals sections, and into a set of non-goals that were consulted repeatedly.
  3. Ingestion. A Python script turns each PDF into page-delimited text, detected tables, a page map from the document's bookmarks, and a rendered image of every page. The renders matter: text extraction scrambles multi-column tables and charts, and an agent can read a page image accurately when the text layer fails.
  4. Synthesis. The agent read every source end to end (for the 425-page Stanford index, the three chapters in scope) and wrote a fixed-structure set of notes per source: document facts and method, findings with page numbers, every chart's values, sponsor or framing caveats, and observations connecting it to the other sources. A written procedure for this step meant a fresh session could take the next source without prior context. For the larger reports, four sources were synthesised in parallel by forked sessions that each wrote only their own file.
  5. Web research. The agent listed candidate sources with their access conditions: open, gated behind a sign-in, or summary only. The human downloaded the gated ones. The agent never attempted to bypass a sign-in. Each new source then went through the same ingestion and synthesis, and the findings were merged into the data files with the evidence level of each insight raised where a second independent source agreed.
  6. Website. A static site with no build step, one page per section, every number read from JSON at run time. Each page was built, screenshotted at desktop and phone width in both themes, corrected, and only then ticked. Deployment is a small GitHub Actions workflow that publishes the site folder on every push.
  7. Chat. An ask-the-report chat was planned and deliberately paused, so that the launch would not depend on a server or an API key. The search on this site is deliberately keyword-based, and says so.
  8. Quality and launch. A colour pass, an originality check of all site text against every source extraction, and an accuracy pass in which a sample of statistics and insights is re-checked against the cited pages. Maintenance steps for adding sources later are already in the plan.

The working rhythm

A typical step went like this. The human names the step or simply says "continue the plan". The agent reads the plan, restates the step, does the work, runs the checks, takes screenshots and reads them, fixes what it finds, records the step in the plan and reports in a few lines. The human looks, sometimes at the live site, and says "push", or asks for a change. Nothing was committed without that yes.

Two things were changed on purpose partway through. For the research phase, the rule was one source at a time with a report after each, because the human needed to see the note quality before trusting the process. Once it was trusted, the remaining sources and the whole website phase were run without checkpoints, each step committed as it landed. Knowing when to remove the checkpoints was a human call, made on evidence.

The agent also kept a review harness for its own use: a script that starts a local server, renders a page in a headless browser, saves a desktop screenshot and a phone-width screenshot, and prints the size of the rendered page so that an empty page is caught immediately. A second script checks every internal link and anchor on every page and reports console errors. Both were written by the agent for the agent, and both ran before every tick.

If you are starting out

Ask the agent to show you what it built, not to tell you. A screenshot it has read itself is worth more than a paragraph saying the page works.

If you run teams

Give the agent a deterministic review harness early and make it part of the definition of done. Checkpoints are a dial: tighten them while trust is low, loosen them when the output has earned it, and write the change down.

Rules that kept it honest

  • Our own words. Every sentence on the site is written by us. One source is a licensed report, and the rule for it is absolute: no verbatim text, not even a short quote, no images, no reproduced charts. The other sources are restated the same way.
  • A reference on everything. Every insight, statistic and vendor fact carries a source id and a page number or URL. A validator refuses data whose references do not resolve to a registered source and page range.
  • Evidence levels. Each insight is labelled multi-source, single source or our analysis, so a reader can weigh it. The validator checks that a multi-source insight really cites two sources.
  • Numbers live in data, never in pages. Not one statistic is typed into HTML. Pages read the JSON files and render what they find, so a corrected figure changes everywhere at once.
  • Generated files are never edited by hand. The search units and the search index are built from the curated files by scripts and rebuilt on every data change.
  • An originality check. A script scans every piece of site text for eight-word runs that also appear in any source extraction and writes a report. Every match against the licensed source was rewritten; the rest were reviewed.
  • Nothing licensed in the repository. The source PDFs, the extractions and the working notes are excluded from version control, and a check runs before every commit to confirm none of them is staged. The repository is public, so this was treated as a hard rule from the first commit.
  • Where sources disagree, say so. Two venture firms rank different model vendors first, and each is an investor in the vendor it ranks first. The site presents both, with their samples and their conflicts of interest, and never declares a winner.

Engineering choices

Static, no build step, no framework. Plain HTML, one stylesheet, a small shell script that renders the header, navigation and footer on every page, and one script per page. A newcomer can read all of it, and an agent can edit it without a toolchain. It costs nothing to host and will still work in ten years.

Data as JSON with a written schema. Six curated files: sources, insights, statistics, vendors, glossary, taxonomy. A schema document describes each record shape and the id conventions, so every session produces the same structure. Ids are stable and used as anchors, so a link to a specific insight or statistic will keep working.

Design tokens, two themes. Colours, spacing and radii are variables on the root element. The dark theme redefines the variables, once for the system preference and once for the reader's stored choice. Chart colours were validated for contrast against both backgrounds before any chart was drawn.

Charts from data, rebuilt not copied. Every chart is drawn from the statistics file with our own styling and has a data table behind it. No source image appears anywhere.

Search in the browser. An inverted index is built from the search units at publish time. The page matches word prefixes, requires every word to match, and ranks by word rarity with a boost for title matches. It is not semantic search and not retrieval-augmented generation, and the search page explains the difference, because readers should know what kind of tool they are using.

Accessibility as a default. Skip link, keyboard-operable everything, focus rings, a native dialog for vendor profiles, reduced-motion support on the one animated element, and text in text colours rather than chart colours.

Three bugs, and what they teach

The blank screenshot. The vendors page opens a profile in a native modal dialog. Screenshots of that state came back blank. The agent worked out that the headless browser paints a top-level page blank while a modal is open, and fixed the harness rather than the page: the screenshot is now taken through a same-origin frame. Lesson: when a test fails, first ask whether the test is right.

The nested links. Stat tiles on the home page were links, and each contained reference links. Browsers refuse to nest one link inside another and silently eject the inner one, which moved the references outside their tiles. The container became a plain element with the link elsewhere. Lesson: some HTML rules are enforced by silently rewriting your document, and only a screenshot shows it.

The sphere that was not a sphere. The search page's tag globe first shipped spinning only about a vertical axis on a stretched ellipse. Live, it read as tags sliding along six rows. The human said so in one sentence. The agent explained the geometry, changed the projection to a circle with perspective, tilted the axis so the globe tumbles, and smoothed the hover pause that had been stuttering. Lesson: the agent's own screenshots were true but insufficient, because a still image cannot show motion. Some review has to be done by a person on the live site.

Takeaways

For people starting out

  • Write a plan file and an instructions file before the first prompt. Make the agent read the plan every session.
  • Ask for one step at a time. Look at each result. Say yes before anything is committed.
  • Ask the agent to screenshot its own work and read the screenshot. Ask it to write a checker for anything it will do more than twice.
  • Keep secrets, licensed material and raw downloads out of version control from day one. Ask the agent to add the exclusion before the first commit.
  • When something looks wrong, say what you see in plain words. The agent can usually find the cause from a good description.
  • Read what the agent writes into the plan. That is where you learn what it actually did.

For seasoned developers and leads

  • The plan is the state, the agent is stateless. Design the plan's sections for a reader who was not there: status block, ticked steps with verification notes, decisions with reasons, open questions.
  • Scope discipline is a written rule, not a hope. Future work goes into the plan as a step, never into the current diff.
  • Separate curated data from generated artifacts, validate the curated data, and regenerate the rest. Never let an agent hand-edit a generated file.
  • Build the review harness before the pages. Headless screenshots at two widths and two themes, a link and anchor checker, a console-error check, and a pre-commit grep for anything that must never be published.
  • Parallelise where the work is separable and the outputs do not overlap, for example one forked session per source, each writing only its own file. Merge sequentially.
  • Checkpoints are a dial tied to evidence. Record in the decisions log when you loosened them and why.
  • Give the agent taste through examples, not adjectives: one finished page or one finished note becomes the model for the rest.

See for yourself
